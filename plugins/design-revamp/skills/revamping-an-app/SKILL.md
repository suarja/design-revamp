# Revamping an app

The whole-app sibling of revamping-a-screen. It composes design-bank (references),
canvas-generation (boards), explainer-mascot-poses (the character) and codex (the
implementation). Proven on Be Viral AI in October 2026: a dark editorial app became a
cream pastel app carried by a mascot, through nine boards and seventeen agent lots,
with the owner deciding at every gate.

The rule that holds everything: **design every screen first, get every board
approved, then code.** The owner said it plainly after an early start on code; the
boards are what agents implement and what the owner judges.

## 1. Read the app as it is

- Capture the real screens on a simulator before drawing anything.
- List the navigation **from the code** (tab layout, routes), never from an old
  capture or store screenshot. A board once drew four tabs from an old capture
  while the code had three; the error survived two boards.
- Take the copy from the localisation files, the cards' props and the real data
  shapes. A board with invented copy cannot be implemented faithfully.
- Draw the screens that are coming as well as the ones that exist: a direction chosen
  on today's screens alone gets redone when the next feature lands. Read the plans and
  mark each upcoming screen as a proposal on the board.

## 2. Choose a direction

1. Draw three directions on one canvas, each on the same three or four key screens,
   with real content. Different structures, not three palettes.
2. The owner picks one. Expect iterations on **colour density**: Be Viral went
   v1 too colourful (full-colour headers) → v2 muted ("low energy, no spark") → v3
   accepted: one pastel block per screen, pastel in two or three elements, the rest
   cream and white.
3. Write the direction as a table the agents can apply without you:

| Element | Rule | Example |
| --- | --- | --- |
| Ground | one light ground everywhere | cream |
| Ink | text, borders 1.5 px, hard shadows 3 px | `3px 3px 0` |
| Function colours | one colour per product function, full + pastel | coach lilac, studio butter, brand coral |
| Header | a pastel block of the function's colour with the mascot in it | coach: mascot holds a phone |
| Parsimony | pastel fills two or three elements per screen | no full-width colour band |
| Navigation | dark floating bar, active tab = pill of its colour + label, inactive tabs keep their label | |
| Buttons | primary = brand colour, ink border 2 px, hard shadow 4 px, **ink text** | white on coral fails contrast |

## 3. Give the app a character

Use explainer-mascot-poses: four candidate characters, two test poses each, the owner
chooses. Then an app pose bank, one pose per state it must carry: hello, phone,
thinking, idea, celebrating, pointing at you, magnifier (analysis running), presenting
a report (analysis ready), crown (premium), shrug (empty and error), front view
(splash). Keep raw, cut and trimmed copies with their prompts.

## 4. Tokens before screens

The first code lot only remaps the existing colour and type tokens (keep the keys,
change the values; add named function colours) and swaps the font. Check one screen
in the simulator, then a lot that removes every hard-coded colour and adds a lint
rule refusing colour literals outside the constants.

## 5. Boards, one per screen group

Onboarding, the core tabs, reports, settings, paywall, then states. Each board is
HTML with real fonts and the mascot's real poses, rendered to an image the owner reads
at 100 %. Before drawing a group, read its section in the practices by screen type that
revamping-a-screen carries. Rules that saved rounds:

- The legend under each phone is part of the spec; agents implement it.
- Numbers you do not have are marked **ex.** on the board; text generated by the
  product is written for one realistic example account and said so. These marks are
  board annotations: check that none leaks into the app's own strings.
- Every departure from the current product is labelled "Proposition" in the legend
  and asked as a question at the end of the message. Never present your taste as the
  owner's decision.
- Before sending, look at the whole render: the mascot hiding a label, an orphan
  « ? » or « : » (use non-breaking spaces in French), a phone with an empty bottom
  half, legal text the store requires (the auto-renewal notice on every paywall
  variant).
- One verdict per board; write each decision into the plan the moment it is given.
- Dense detail pages (a profile, a settings page) get a board of their own when the owner
  finds them cramped: one card per section, body text at 16, section titles instead of
  small grey labels.

### The states board

Never a blank screen with a grey spinner. The mascot shows what is happening, one
sentence says what comes next, one button offers the next step when there is one.
The native splash and the first JavaScript loader show the same image at the same
place, so the hand-off does not jump. A failing store or network call ends on a
stable screen with "Retry", never on a loop.

### The copy board

Once the screens are built, rewrite the words of the conversion path (welcome, sign-in,
onboarding, paywall) on their own board, before any capture for the store:

- Open with the voice in four rules the agents can apply, e.g. the mascot says "I", short
  sentences; an outcome for the user, never the mechanism (workflow, data, scraping); every
  promise points to *their* account; no promise the product cannot keep (no revenue, no
  "dominate").
- One row per string: the current screen capture, the current text struck through, the
  proposal, the reason. Mark product changes (moving a review prompt, dropping a step) as
  "Proposition" so they are decided, not slipped in.
- When the owner rejects an expression ("in your voice" was not understood), replace it
  everywhere it appears, not only on the line he pointed at.
- Audit the texts the **backend model** writes too: the greeting and reveal prompts produced
  "unlock your viral potential" and a Pro pitch in the second message, untouched by the app
  copy. Messages already stored keep the old wording; only a fresh run shows the new one.
- Rewrite every locale with the same intent, not word for word.

### Icon and splash

Generate four icon options and judge them masked with the iOS corner radius
(22.37 % of the side) at 120, 60 and 40 px. The mascot's face filling the square read
best by far. Generated art often has white rounded corners: fill them with the edge
colour before export. Icon and splash are **native**: they reach users only with a new
binary, never through an over-the-air update.

## 6. Delegate in reviewed lots

One brief file for all agents (state, where to work, the approved boards per lot,
the owner's decisions, verification, report format). Mechanical lots go to the cheaper
model, design lots to the stronger one. After each lot, review its simulator captures
yourself against the board before launching the next; collect small deviations and
batch them into one follow-up lot. Each lot reports typecheck compared with the
baseline list (not only the count), targeted tests, lint, captures named after the
lot, and what it observed versus supposed. Delete a lot's section from the brief once it
is merged; git keeps it.

Agents overreach on behaviour: asked to move one review prompt out of onboarding, one
disabled every other review trigger. Read the diff of any lot that touches a service, not
only its captures.

Touching a fragile area (a chat feed built from persisted state) is safe when the change
is at render only: filter what is displayed, leave the state the step logic reads.

**Shared machine.** The owner's bundler serves the agents' worktree, so he sees a lot
while it is being written: say so, or point his bundler at a stable branch. Reserve one
simulator for him and name it in the brief. Agents never stop a process they did not
start (a simulator streaming helper killed a foreign listener on its own). Reports go next
to the captures, not into the app repository. Two agents never work in the same worktree at
once: queue the second lot.

**Without credentials.** Agents do not sign in to remote identity providers. The owner
signs in once on the simulator and the session persists; otherwise a temporary
development-only preview route mounts the real components with fixture data and is
deleted before the commit. A development payment-simulation switch covers the paywall.
On a shared machine, each agent runs its own bundler on a free port and never stops
the owner's.

## 7. Deliver

Merge the lots into the integration branch, then put a development build with the
**real bundle identifier** on the owner's phone: a test bundle identifier makes the
store's product lookup fail and looks like a payment bug. JavaScript changes then
reach the phone live; native ones (icon, splash) need a rebuild. Publish the
over-the-air update against the runtime of the binary users actually have.

Store screenshots come last, from real captures of the shipped design, on the simulator
size the store requires, with an account the owner owns and signs into himself (never a
third party's public account). Their argument and thread are designed before that, on a
canvas: follow [the store screenshots method](references/store-screenshots.md). Plan the
store page's header and search-results visuals in the same pack, and verify their sizes
in the store's documentation before export.

A shared development backend may be running another branch than the integration
branch. Deploying the integration branch can then fail (a schema field it does not know)
or erase the other work. Stack your commits on the deployed branch in a throwaway branch,
deploy that, and record it.

## Traps seen

| Symptom | Cause | Fix |
| --- | --- | --- |
| Pale tints became saturated fills after the hard-coded colour sweep | `rgba(…, 0.1)` mapped to the full token | soft and border token variants; a translucent literal becomes a translucent token of the same role |
| Title illegible on a photo after the light remap | ink text kept on a dark photo | white text on an overlay, or drop the photo |
| Board shows the wrong navigation | drawn from an old capture | read the tab layout in the code |
| Mascot looks ghostly on the splash | cut-out made pale parts semi-transparent | the repair script of explainer-mascot-poses |
| "Le Replay n'a pas pu…" after renaming the coach | the article of the old common noun kept | search articles before the new name in every locale |
| Phone app "refreshes in a loop" | not reproduced; suspected paywall retrying the store's offerings | bounded loading, stable error with retry |
| Agent stops at the sign-in screen | expected, by rule | plan the owner's one-time sign-in |
| "✓ Saved" chips pile up in the chat after onboarding | frozen confirmation components rendered as history | hide frozen items at render only; the step logic keeps reading the stored state |
| Paywall header under the status bar, empty space below | native full-screen modal outside the safe-area provider | a safe-area provider inside the modal screen |
| Inactive tabs show only an icon | label rendered for the active tab only | label on every tab, muted colour for inactive ones |
| A foreign-script word inside generated French text | prompt said "Respond in fr" (code, not name) | language name in the prompt, plus a post-generation script check with one retry |
| Store review asked during onboarding | prompt placed before any value | ask after the first real result (first script) |
| New account cannot analyse its own handle on the dev backend | handle already owned by an old test user | rename the old row's handle (reversible) rather than deleting it |
